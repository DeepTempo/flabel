# Engineering Review — flabel PRD

**Reviewer:** staff engineer, fresh eyes · **Artifact:** `docs/prd.md` v0.3 (2026-08-11) · **Verdict:** not ready for `/project:plan` as written

The Tier 2 half of this PRD (ingest → Zeek → Suricata → consolidate → write run directory) is buildable, well-reasoned, and could plausibly be delivered in a couple of weeks by one person with AI assistance. The Tier 1 half — replaying captures past a Palo Alto VM-Series in a GCP lab — is roughly 60% of the total effort, carries all the schedule risk, all the recurring cost, and is the only part that cannot be tested in CI. **The single biggest problem is that Tier 1 may not be physically possible in the environment chosen for it:** PAN-OS documents the VM-Series in public cloud as Layer 3 only (virtual-wire and tap are on-premises deployment modes), and a GCP VPC is a Layer 3 fabric with source-IP anti-spoofing — meaning a `tcpreplay` of a capture's original Ethernet and IP headers will very likely be discarded by the network before it ever reaches the firewall. Research decision 3 (vwire) and decision 7 (GCP lab) may be mutually exclusive, and nothing in the PRD tests that assumption. Second-biggest: **Goal 2 (reproducibility) is unachievable as specified**, because Zeek's `uid` — which the PRD makes the authoritative flow identity embedded in every label — is derived from a per-run random seed and changes on every run. Two runs of the same capture will never produce byte-identical `labels.json`, and labels from different runs cannot be joined to each other. Both problems are cheap to settle with short spikes and expensive to discover during build.

---

## The three hardest parts

**1. Making a Palo Alto VM-Series in GCP actually see a replayed capture (§6.4, §5 "Environment", §10 "Infrastructure").**
This is not "configure a firewall." It is: a cloud build, a commercial licence with a threat-prevention subscription, a network topology that has to carry frames a VPC is designed to drop, a bidirectional-replay problem (a firewall needs to see both sides of a session from the correct interfaces to build session state), a stateful-inspection problem (captures that begin mid-flow have no SYN, and PAN-OS discards non-SYN TCP sessions by default), a fidelity-measurement problem (sent-vs-seen at packet granularity), a clock problem, a log-retrieval problem with unverified API syntax (Open Q7), and a concurrency problem (Open Q5). Every one of those is a separate way for Tier 1 to silently produce fewer labels than it should. The PRD treats it as one bullet list of five business rules.

**2. Correlating detections back to a Zeek flow identity (§6.5).**
The PRD identifies this risk for Tier 1 only. It is also non-trivial for Tier 2: Suricata's notion of a flow is not Zeek's, port reuse within a single capture makes a 5-tuple ambiguous, alerts can fire on tunnelled inner flows whose tuple never appears in `conn.log`, and Suricata alerts on packets Zeek may not log as a connection at all. The design's honesty here is good (`unmatched_detections[]`, never guess) but that honesty converts a correctness bug into a coverage gap, and no target or alarm threshold is set for that gap (§11 explicitly sets no target). A run where 40% of detections went unmatched and a run where 0.1% did are both "successful."

**3. Genuine bit-for-bit reproducibility across a four-tool chain (Goal 2, US-07, §11).**
Reproducibility requires simultaneously pinning: Zeek's random seed, Zeek's version, Suricata's version, Suricata's thread mode and output ordering, the exact admitted rule set, and a canonical JSON serialisation (key order, timestamp formatting, array ordering). The PRD names none of these controls and asserts the outcome. This is the kind of requirement that looks like one test and is actually six design decisions.

## Findings

### [CRITICAL] Tier 1 as specified may be physically impossible in the chosen environment
**What it means:** Research decision 3 selected a virtual-wire pair; decision 7 put the lab in GCP. These are likely incompatible. PAN-OS documents public-cloud VM-Series interfaces as Layer 3 only — virtual wire, Layer 2, and tap are on-premises deployment modes. Separately, a GCP VPC is not a Layer 2 network: it does not carry arbitrary Ethernet frames, and it drops packets whose source IP is not one the instance is authorised to send. A packet capture replayed with `tcpreplay` carries the *original* capture's MAC addresses and source IPs — exactly the traffic a VPC is built to discard. The research's supporting evidence for vwire is a Palo Alto community forum post about replaying at a physical device; it does not establish that this works in a cloud VPC. §10 records "PANW deployed as a virtual-wire pair, per Palo Alto's replay guidance" as a settled architecture decision on that basis.
**Cost of ignoring:** The most expensive requirement in the project gets planned, issued, budgeted, and half-built before someone discovers the packets never arrive. Recovery means either relocating the lab to on-premises/nested virtualisation, rewriting every packet's addressing (which destroys the flow tuples the entire correlation design depends on), or dropping Tier 1 — a change that invalidates §6.4, §6.5's tiering, Goal 5, US-08, and the trust hierarchy in one go. This is a weeks-to-months rework discovered at the worst possible time.
**Recommended change:** Do not enter `/project:plan` until Spike 1 (below) has demonstrated one real threat log produced by one replayed packet in the actual target environment. Add an explicit assumption to §10 stating "vwire replay is achievable in GCP" as an *unverified* assumption with a named owner, and add it to §13 Open Questions as blocking. If it fails, the fallback worth costing is a single host with nested virtualisation and Linux bridges/veth pairs, where a genuine L2 segment exists — or accept an on-premises box.

### [CRITICAL] Goal 2 (reproducibility) cannot be met, because Zeek `uid` is random per run
**What it means:** Zeek generates connection UIDs from a random seed initialised at startup. Run Zeek twice over the identical file and you get identical flows with *different* `uid` values. The PRD makes `uid` the "authoritative flow identity for the entire system" (§6.2) and embeds it in every label (§6.6 schema). Therefore Goal 2's verification method — "byte-identical `labels.json` across two runs, ignoring run-metadata timestamps" — will fail 100% of the time on a capture with any detections. So will US-07's acceptance criterion, test case 11, and the §11 metric "Reproducibility: 100%". Zeek can be made deterministic (it accepts a fixed seed file), but nothing in the PRD requires it. There is a second-order casualty: US-06 exists so a DME can "compare label sets across ruleset snapshots" — with per-run random UIDs, labels from two runs of the same capture cannot be joined to each other at all, which is the entire point of US-06.
**Cost of ignoring:** The headline determinism test fails on day one of build and gets "fixed" the fast way — by loosening the comparison until it passes. That quietly deletes the guarantee. Worse, a DME who assumes `uid` is stable will silently mis-join label sets across runs and train on garbage.
**Recommended change:** Add to §6.2: "Zeek is invoked with a fixed, recorded seed so that `uid` assignment is deterministic for a given input; the seed is part of run provenance." Add to §6.6: `labels.json` is written in a canonical form (sorted `labels` array with a defined sort key, sorted object keys, fixed timestamp format). Restate Goal 2 as "identical after canonicalisation, with the same pinned tool versions and ruleset snapshot," and add tool-version equality to the precondition — a Suricata point upgrade changes which rules fire.

### [CRITICAL] Nine of ten admitted rule sources bypass the only false-positive gate, and one of them isn't a verdict source at all
**What it means:** The research brief records the load-bearing premise: "Because trust isn't modelled per rule, **ruleset curation is the entire false-positive defence.**" §6.3 then applies the `confidence == High AND signature_severity in (Major, Critical)` filter to ET Open only; abuse.ch (×4), malsilo, stamus/lateral, the-hunters-ledger, and pawpatrules are "admitted wholesale." The per-source rationale (research A3) is sound as far as it goes — IOC feeds have no per-rule confidence to filter on — but the conclusion isn't "therefore they're safe," it's "therefore they have no gate." pawpatrules is admitted with an FP review still open (Open Q9), i.e. the PRD ships an unvetted source into ground-truth training data and tracks the vetting as a question. Worse, research A2 admits `oisf/trafficid` with the note "identification only, contributes no verdicts" — but §6.3 encodes no distinction between verdict and non-verdict sources. If those rules are loaded into the same Suricata instance, they fire alerts, and every alert becomes a Tier 2 malicious label. The PRD has no mechanism that would prevent that or notice it happened.
**Cost of ignoring:** Systematically false malicious labels in training data, with complete-looking provenance blocks attached. This is precisely the failure §1 names as "the expensive failure" — and the pipeline has no way to detect it, because there is no FP measurement (§2, "explicitly not a goal").
**Recommended change:** Three specific edits to §6.3. (1) Classify every source as `verdict` or `non-verdict`; non-verdict sources are either not loaded or their alerts are routed to enrichment and can never become a label. Add an acceptance criterion and a test asserting no `oisf/trafficid` SID appears in `labels`. (2) Make wholesale admission an explicit, named policy per source in run provenance (`admission_basis: metadata-filter | wholesale`), so a downstream consumer can filter out ungated sources. (3) Resolve Open Q9 before v1 or drop pawpatrules; "admitted pending FP review" is not a state ground-truth data should ship in.

### [HIGH] IOC-indicator rules will attach malicious labels to benign infrastructure flows
**What it means:** URLhaus, Feodo Tracker, and SSLBL rules match indicators — a C2 IP, a URL string, a certificate, a DNS name. When a urlhaus DNS rule fires, the flow that carried the lookup is the flow **to your own resolver**. When an HTTP-URL rule fires behind a proxy, the labelled flow is the flow to the proxy. The label is *correctly derived from a correctly-firing rule with perfect provenance* — and it marks a benign infrastructure flow as malicious. §6.5 consolidates per flow and §6.6 emits `verdict: "malicious"` with no field distinguishing "this flow is the malicious activity" from "this flow merely referenced a malicious indicator." Nothing in §9's acceptance criteria or §11's metrics would surface this.
**Cost of ignoring:** A model trained on this learns that traffic to 8.8.8.8, or to the corporate proxy, is malicious — the highest-volume, most-benign flows in the dataset. This is a worse outcome than a random false positive because the error is correlated and repeated.
**Recommended change:** Add to §6.6's source entry: the rule's `classtype` and app-layer protocol, plus a required `label_basis` field distinguishing direct-malicious-flow from indicator-reference. Add a §6.3 rule: alerts on flows whose destination is an operator-declared infrastructure host (resolver, proxy) are emitted as indicator-references, not verdicts. At minimum, make the distinction machine-visible so a DME can exclude them — the PRD's own philosophy is that a consumer should never have to guess.

### [HIGH] There is no ruleset-snapshot lifecycle, and Goals 1 and 2 both depend on one
**What it means:** §6.3 requires "the admitted rule set is snapshotted per run — source, version, and date," and §6.6 requires provenance to list "ruleset snapshots per source." But nothing says *when rules are fetched*, whether a run touches the network, how a snapshot is named, or how a previous snapshot is re-used. US-07 and test case 11 both say "the same ruleset snapshot" as if a snapshot were an addressable object you can pass to a run. It isn't defined as one anywhere. If a run fetches rules itself, Goal 2 is impossible (every run differs) and `--offline` is a misnomer. If it doesn't, someone must produce snapshots by an unspecified mechanism, and US-06's "compare across ruleset snapshots" has no way to pin the older one.
**Cost of ignoring:** The implementer picks one — probably "fetch at run start," the easy path — and reproducibility dies quietly. Or the reproducibility test passes only because two runs happened within the same hour.
**Recommended change:** Make the snapshot a first-class artifact with its own lifecycle. Add to §6.3: a separate command (`flabel rules update`) fetches, filters, and writes an immutable snapshot directory whose identifier is a content hash of the emitted filtered rule file; a labelling run takes `--ruleset-snapshot <id>`, defaults to the newest available, and **never performs network I/O**. This one change makes Goal 2 achievable, makes US-06 real, makes Goal 1's snapshot field meaningful, and removes network flakiness from every test.

### [HIGH] Tier 1 labels have no ruleset-snapshot provenance, which violates Goal 1
**What it means:** Goal 1 requires every label to record "the ruleset snapshot in use." §6.4 specifies nothing equivalent for PANW — no threat-content release version, no application-content version, no PAN-OS version. The §6.6 sample Tier 1 source entry carries only `threat` and `detected_at`. A PANW detection's meaning is entirely determined by the content release loaded on the device, which auto-updates. So the highest-trust tier is the one tier whose labels are not reproducible or auditable, and AC US-02's escape hatch — "the firing rule identity **where applicable**" — makes the gap untestable, because a schema check cannot distinguish "not applicable" from "we forgot."
**Cost of ignoring:** Goal 1's headline claim ("100% of labels carry a complete provenance block") is true only because "complete" is defined per-source and Tier 1's definition is empty. Six months later nobody can say which content version produced a Tier 1 label.
**Recommended change:** Add to §6.4: the run records PAN-OS version, threat content release version, and application content version, retrieved from the device at run time; each Tier 1 source entry carries the PANW threat ID as its rule identity. Replace "where applicable" in AC US-02 with an explicit required-field table per source class, so the automated check is exhaustive.

### [HIGH] `detected_at` on a Tier 1 label contradicts §6.4
**What it means:** §6.4 states plainly: "Detections are stamped at replay time, not capture time. Labels reference the **capture's** timeline; replay time is never emitted as a label timestamp." The §6.6 sample schema then shows `{ "tier": 1, "source": "panw", "threat": "...", "detected_at": "..." }`. Either that field holds replay time — violating the rule — or it holds a capture-timeline value produced by a replay-time-to-capture-time mapping that no section specifies, and which research C3 explicitly warns "is not 1:1."
**Cost of ignoring:** The implementer copies the schema (implementers always copy the schema) and emits replay time. Every Tier 1 label then carries a timestamp from a different timeline than its flow, and a DME doing time-window feature extraction gets nonsense. This is a silently-wrong-data path.
**Recommended change:** Either delete `detected_at` from Tier 1 source entries (the flow's `ts_first`/`ts_last` already give the capture timeline) or rename it `device_observed_at` and document in the schema that it is replay-clock and must never be interpreted as capture time. State the choice in §6.6, not just in prose.

### [HIGH] Replay realism: unidirectional, mid-stream captures will lose most Tier 1 detections, and the packet-count alarm will be permanently on
**What it means:** §6.4 says only "replays the normalized capture past a PANW VM-Series." Two mechanics are missing. (a) **Direction.** A stateful firewall needs client traffic on one side of the vwire pair and server traffic on the other. Replaying a whole capture out one interface presents both directions from the same side; sessions will be malformed or dropped. The standard mechanism (`tcpprep` to build a client/server split cache, then a dual-interface replay) is not mentioned anywhere in the PRD or research. (b) **Mid-stream flows.** Real captures routinely begin mid-connection. PAN-OS by default rejects TCP sessions that don't start with a SYN, so those flows get no inspection and produce no detections — a missing label, invisible in the output.
**Cost of ignoring:** Tier 1 appears to work (it produces *some* labels) while systematically missing a large, unmeasured fraction of the capture. Simultaneously, "packets sent equals packets seen" will mismatch on essentially every real capture for entirely legitimate reasons, so Goal 3's fidelity alarm becomes a constant amber that everyone learns to ignore — which destroys its value as a signal for the case it was built for.
**Recommended change:** Add to §6.4: the replay uses a `tcpprep`-derived client/server split across the vwire pair, and the split cache is recorded in provenance. Add an explicit requirement to record and report, per run: sessions the device rejected as non-SYN, and the device's non-SYN policy setting. Redefine the reconciliation check as "packets sent vs. packets seen, with device-side legitimate-discard counters accounted for separately," so the alarm means something. Spike 2 should measure the real numbers before this is planned.

### [HIGH] "Zero silent-drop paths" (Goal 3) is not a verifiable claim as written
**What it means:** Goal 3's verification is "Every such condition has a corresponding field in the `run` block; zero silent-drop paths." Checking that a field *exists in the schema* does not check that code populates it when the condition occurs. And "zero silent-drop paths" is an unbounded negative — you cannot test the absence of unknown paths. §11 backs it with "code review plus tests," and code review is not an automatable gate.
**Cost of ignoring:** The strongest-sounding goal in the document is the one with no real test behind it, which is exactly the shape of a guarantee that fails in production. Given this output is training data, a silent drop is the failure mode with the longest blast radius.
**Recommended change:** Replace with a closed, numbered list of loss conditions (truncated input; replay packet mismatch; device-rejected sessions; uncorrelated detection; multi-datalink split discard; ruleset fetch failure; Zeek/Suricata non-zero exit; PANW query returning fewer logs than expected), each with a named `run`-block field and **one fault-injection test each**. Restate the goal as "every enumerated loss condition is reported in the run block" — a claim that can actually pass or fail.

### [HIGH] Licensing exposure: rule text is copied into a commercial artifact with no attribution, and JA4+ is recorded as "approved" when it should be blocked
**What it means:** Two separate problems. (a) The `threat` field in §6.6 is, in practice, the Suricata rule's `msg` string, copied verbatim. Admitted sources include GPL-3.0-only (`stamus/lateral`), CC-BY-SA-4.0 (`pawpatrules`), and CC-BY-4.0 (`the-hunters-ledger`) — the last two carry attribution requirements and the middle one share-alike. The PRD has no per-source licence field in provenance and no attribution output. Research recorded the licences but only assessed the linking question, not the "we are copying their text into a commercial training artifact" question. (b) §10 says JA4+ under FoxIO License 1.1 (non-commercial) is "**approved** for use pending Legal's assessment, since flabel output feeds product models," and research decision 6 records "JA4+ approved." Open Q3 simultaneously calls it "Open — blocking 6.2 scope." Those cannot both be true, and the resolved decision has the safe default backwards: you do not adopt a non-commercial-licensed component into a commercial pipeline and then ask Legal.
**Cost of ignoring:** (a) is a compliance defect baked into every output file, discovered by someone else. (b) is worse: build proceeds on JA4+, Legal says no, and §6.2 plus every JA4+-derived feature has to be torn out — after models have been trained on it.
**Recommended change:** (a) Add a per-source `licence` field to ruleset snapshot provenance, and emit a `NOTICE` file per run listing every source that asserted a label with its licence and required attribution. (b) Change §10 and §6.2 to make **plain JA4 (BSD-3-Clause) the v1 default**, with JA4+ behind a flag that is off until Legal signs. Correct research decision 6, which is recorded as resolved and is not safe. Flag to Craig: this is a lawyer's call, not an engineer's — the recommendation here is only about which default is safe while you wait.

### [HIGH] Tier 1's recurring cost is unbudgeted, while a $900/year ruleset was rejected on cost
**What it means:** §4 excludes ET Pro at "~$900/sensor/yr" as not worth it for v1. §5 and §10 then require a PANW VM-Series in GCP. A VM-Series produces threat logs only with a Threat Prevention (or Advanced Threat Prevention) subscription — without it, Tier 1 detects nothing and the top of the trust hierarchy is empty. Marketplace PAYG bundles are billed hourly on top of compute; a lab left running is plausibly four figures per month. No figure for this appears anywhere in the PRD, the research, or the risk table.
**Cost of ignoring:** The project's cost profile is dominated by an unexamined line item, and the one cost that *was* examined was rejected for being 1–2% of it. A PM discovers this from a GCP bill.
**Recommended change:** Add a row to §10 Dependencies stating the VM-Series licensing model (BYOL auth code vs. Marketplace PAYG), the required subscription, and an estimated monthly lab cost including a lab-shutdown-when-idle assumption. Add an Open Question with Craig as owner. Then re-ask the ET Pro decision with both numbers side by side — it may be that the cheapest route to more high-confidence labels is the ruleset you already rejected.

### [HIGH] Multi-datalink handling has no defined downstream semantics
**What it means:** §6.1 says "Multi-datalink captures are split before conversion," and AC US-09 says such a capture is "split before conversion and processed without error." Splitting yields *N* files. §6.1 also requires that "all three consumers receive the **same normalized file**" (singular), and §6.6 produces exactly one `labels.json`. So: does flabel process all N, or one? If all N, that is N Zeek invocations whose `uid` namespaces are independent (making `uid` non-unique across the merged logs, breaking AC US-03's "exactly one matching flow record" and Goal 4's flow identity), plus N replays with possibly incompatible link types. If one, the other N-1 are silently discarded and the run reports full coverage.
**Cost of ignoring:** The most likely implementation is "take the first/largest and proceed," which is a silently-incomplete label set with a clean bill of health — the exact class of failure Goal 3 exists to prevent.
**Recommended change:** Pick one and write it down. The cheapest defensible option: a multi-datalink capture processes only the dominant link type, stamps `input_status: partial` with the discarded packet count and the link types dropped, and warns. If you keep the split-and-process-all option, §6.2 must additionally require a per-split `uid` namespace prefix, and AC US-03 must be restated in terms of the namespaced identity.

### [HIGH] Every Tier 1 acceptance criterion will only ever be tested against a mock
**What it means:** `CLAUDE.md` states "Never call external APIs or real devices in tests (mock them)." The lab does not exist. That means AC US-01 bullets 1 and 4, AC US-03 bullet 2, AC US-04 (both tiers), AC US-05 bullet 2, and test cases 1, 8, 13, and 14 will be validated exclusively against a fake PAN-OS that the same author wrote — a mock that encodes the author's *assumptions* about the device's behaviour, which is exactly what's in doubt (log latency, filter syntax, packet drops, non-SYN handling). Every one of them will pass while telling you nothing. Meanwhile §11 says provenance and reproducibility are "measured in CI," but `.github/workflows/ci.yml` is `ubuntu-latest` + `uv sync` — it has no Zeek 6+, no Suricata 8+, no `editcap`, no `zkg`, so it cannot run the pipeline at all today.
**Cost of ignoring:** A green build and a full acceptance-criteria checklist that constitute no evidence about the half of the system carrying all the risk. This is the "why didn't CI catch it" gap, visible in advance.
**Recommended change:** Split §9 into criteria testable in CI and criteria requiring the lab, and mark each. Add a distinct **on-device acceptance checklist** that must be executed manually against the real firewall, once, and its results recorded in the repo. Add a scaffold requirement for a pinned toolchain container (specific Zeek, Suricata, Wireshark versions) that CI uses — this is also a prerequisite for Goal 2, since reproducibility across unpinned tool versions is meaningless.

### [MEDIUM] Per-rule `confidence` in the schema contradicts a recorded decision, and is absent for most sources
**What it means:** The research brief's non-negotiable decisions state: "Trust is **per-source**, not per-rule… Per-rule confidence metadata is *not* modelled in the output." The §6.6 sample label emits `"confidence": "High"` on the Suricata source entry. Beyond the undeclared drift, it creates a schema that is heterogeneous in an undocumented way: ET Open labels will carry `confidence`, wholesale-admitted IOC-feed labels cannot, so the field is sometimes present and sometimes absent with no stated meaning for its absence.
**Cost of ignoring:** A DME writing a filter on `confidence` silently drops every IOC-feed label, or treats missing as low. Schema ambiguity in training data propagates invisibly.
**Recommended change:** Either remove it (consistent with the recorded decision) or keep it and document it properly: make it `confidence: High | null` with `null` explicitly meaning "source has no per-rule confidence taxonomy," and pair it with the `admission_basis` field recommended above. Also record the drift in the revision history — a decision marked non-negotiable at Stage 1 should not change silently at Stage 2.

### [MEDIUM] Two independent JA4 implementations are used and never cross-checked
**What it means:** §6.2 computes JA4 via Zeek's `zeek/foxio/ja4` package. §6.3 matches JA4 via Suricata's native `ja4.hash` keyword — a separate, independent implementation. Nothing requires the two to agree. US-14's AC checks that a JA4 label is "structurally identical" to other Tier 2 labels; it does not check that the JA4 value Suricata matched equals the JA4 value Zeek recorded on the same flow.
**Cost of ignoring:** A DME pivots from a JA4-derived label to the Zeek JA4 attribute and finds a different fingerprint, with no way to tell which is right. Or a JA4 rule never fires despite the fingerprint being present, because the two implementations differ on an edge case (GREASE handling, QUIC, protocol version encoding) — a silent false negative in a path specifically built to be provably alive.
**Recommended change:** Add an acceptance criterion: on a TLS fixture, Zeek's computed JA4 and Suricata's computed JA4 for the same flow are equal, and both implementations' versions are recorded in run provenance. Add to §6.2 a requirement that the JA4 value carried on a label is the Zeek-computed one, so there is a single authority.

### [MEDIUM] The millisecond clock-sync requirement is unnecessary and adds lab cost
**What it means:** §5, §6.4, and §10 all make millisecond NTP accuracy a hard v1 requirement across three hosts. But §6.4 and §10 also state that correlation is tuple-driven and that time only *scopes the query* — and research C3 says outright that "the correlation design should not depend on it." With a padded query window and tuple matching, second-level accuracy is ample. Millisecond accuracy across three GCP hosts is achievable but it is a real configuration and verification burden, and the risk table already rates clock drift as Low likelihood / Medium impact.
**Cost of ignoring:** Effort and lab complexity spent defending a requirement the design deliberately doesn't rely on — and a v1 acceptance gate that can fail for a reason that doesn't matter.
**Recommended change:** Downgrade to "NTP-synchronised, sub-second, with the query window padded by ±N seconds; correlation must not depend on clock accuracy." Record the padding value. Update research decision 9 to match, noting it was relaxed because tuple matching superseded it. Related simplification: Suricata does not need its own host at all (it reads the file), so the three-host lab can be two — removing one VM and one clock relationship entirely.

### [MEDIUM] Truncation detection and the "truncation offset" may not be obtainable from the tools named
**What it means:** §6.1 promises a truncated capture is processed and stamped with "the packet count reached and the truncation offset." No tool in §10's dependency list reports a truncation offset. `capinfos`/`editcap` typically error on a truncated file rather than reporting where it stopped, and `editcap -F pcap` may refuse the conversion outright — meaning a truncated **pcapng** might not be processable at all, which no requirement covers. Producing an offset reliably means flabel walking pcap record headers itself until a short read.
**Cost of ignoring:** AC US-05 bullet 1 and test case 7 cannot be satisfied as written; someone invents an approximation and the field means something different from what it claims. Or truncated pcapng becomes an unhandled crash.
**Recommended change:** Specify the mechanism: flabel validates the capture by walking record headers itself and derives packet count and byte offset from that walk. Add a distinct requirement for truncated **pcapng** (probable answer: hard failure with a message telling the operator to repair with `editcap`, since a partial pcapng block cannot be safely converted). Add a test case for it.

### [MEDIUM] `.gitignore` will silently swallow the test fixtures the acceptance criteria require
**What it means:** Verified in the repo: `.gitignore` contains `*.log` and `zeek/`. AC US-03, US-10, and test cases 15 and 16 all require golden Zeek output to test against — which is `*.log` files inside a `zeek/` directory. `git add` will silently refuse them.
**Cost of ignoring:** Tests pass on the author's machine and fail or vanish in CI; the usual resolution is weakening the test until it passes without the fixture. The rules exist for a good reason (never commit capture-derived data), so this needs an explicit narrow exception rather than removal.
**Recommended change:** Add negations scoped to the fixtures directory (`!tests/fixtures/**/*.log`, `!tests/fixtures/**/zeek/`) as part of scaffold, and fold this into Open Q8's fixture strategy. Keep the broad ignores.

### [MEDIUM] Trust-by-construction is treated as unmeasurable when a cheap partial measurement exists
**What it means:** §2 states "explicitly not a goal: a measured false-positive rate," and the risk table rates the unfalsifiability as High/High with a mitigation that is really just record-keeping. Research risk 2 flagged it "for eng-review" — so here is the answer. You cannot measure a true FP rate without a labelled corpus, correctly. But you can measure something genuinely useful for near-zero cost: **run the pipeline over a capture believed benign and count the labels.** Every label is a false positive, by construction. No ground-truth corpus is needed — only one clean capture. The mirror test (a known-malicious public capture from malware-traffic-analysis.net must produce labels) guards the false-negative direction and doubles as the pipeline's end-to-end smoke test.
**Cost of ignoring:** The project's central quality claim stays a matter of faith, and the specific failure modes identified in this review (non-verdict sources leaking labels, indicator-reference mislabelling, unvetted pawpatrules) have no detector. When a DME asks "how noisy is this?", the answer is a shrug — for data being used to train a product.
**Recommended change:** Add Goal 6: "**Specificity canary.** A curated benign capture produces zero labels; a curated known-malicious capture produces labels from both tiers." Add a matching §11 metric (target: zero labels on the benign canary) and a §9 criterion. Add both captures to the Open Q8 fixture strategy. This does not reopen the corpus-validation decision — it is a bounded regression test, not a measurement programme, and it converts an unfalsifiable claim into a falsifiable one for a day of work.

### [LOW] `max_tier` is named for the opposite of what it computes
**What it means:** AC US-04 says `max_tier` is `1` when both tiers assert. Tier 1 is the *highest trust* and the *lowest number*, so `max_tier` is arithmetically the minimum. A DME writing `max_tier >= 1` to mean "high trust only" gets everything; `<= 1` gets the right answer while reading wrong.
**Cost of ignoring:** A filter written backwards in a downstream training script, which produces a plausible-looking dataset. Cheap to prevent now, invisible later.
**Recommended change:** Rename to `best_tier` or `highest_trust_tier`, and state the ordering convention explicitly in §6.6 ("lower is higher trust").

### [LOW] `--offline` is a misleading name
**What it means:** Every path in this tool reads a file offline; Tier 2 is offline by nature. What the flag actually means is "skip Tier 1." It also implies no network use, which — depending on how the ruleset-snapshot question above is resolved — may be false.
**Recommended change:** Rename to `--no-tier1` (or `--skip-ngfw`) and keep `--offline` as a documented alias if you like the word. Update §6.7, Goal 5, US-08, and the §9/§15 rows.

### [LOW] Document hygiene suggests late edits that were not re-integrated
**What it means:** "15. Basic Test Cases" is plain text, not a heading, so it won't appear in a table of contents or render as a section in the published Google Doc; §15 also precedes §14 References. Test-case rows run 1–15, then 17, 18, then 16. US-14 and US-15 sit between US-10 and US-11 in §7. The v0.3 JA4 change is well-argued but was stitched in rather than woven in.
**Recommended change:** Fix the heading and renumber before the document goes to the reviewers and approvers named in Open Q1. A document seeking sign-off should not visibly show its seams.

## Under-specified — implementer will have to guess

Each of these is a decision the PRD leaves open that the implementer *must* resolve to write code. Every one will be resolved silently unless it is written down first.

1. **"Controlled rate"** (§6.4, research decision 4). Is it the capture's original inter-packet timing (`--multiplier 1`), a fixed packets-per-second, or a bounded speed-up? This single number determines the project's entire throughput budget and whether a 1-hour capture takes 1 hour or 5 minutes.
2. **Replay direction and interface assignment** (§6.4). One interface or two; `tcpprep` split or not. See the High finding above.
3. **When rules are fetched and how a snapshot is addressed** (§6.3). See the High finding above.
4. **How the admission filter is actually implemented** (§6.3). `suricata-update`'s model is subtractive (enable everything, then disable); expressing "admit *only* rules where confidence == High AND severity ∈ {Major, Critical}" is an inclusion filter. This probably means flabel parses rule metadata itself and emits its own filtered rule file. That is a real component, not a config line.
5. **Which run-block field names exist** (Goal 3, §6.6). `input_status: partial` is the only one named. The others ("a corresponding field in the `run` block") are asserted but never enumerated — so nothing can be tested against them.
6. **What "identical apart from run-metadata timestamps" means precisely** (Goal 2, AC US-07). Which fields are excluded from the comparison, and by what normalisation?
7. **Sort order of the `labels` array** (§6.6). Required for reproducibility; unspecified.
8. **Tier 2 → Zeek `uid` correlation** (§6.5). The PRD specifies tuple-driven matching for Tier 1 only. Tier 2 needs a rule too, including tie-breaking when a 5-tuple maps to more than one `conn.log` record (port reuse) and behaviour when a Suricata alert has no corresponding Zeek connection.
9. **Whether `unmatched_detections[]` has a failure threshold** (§6.5, §11). "Tracked, no target" means a run that correlated nothing still reports success.
10. **Where the captures come from** (§10 Data & Privacy). Customer traffic, internal traffic, or public corpora? This determines whether there are contractual limits on using them to train a product model — a materially different question from "don't commit them to git."
11. **Retention and location of run outputs** (§10). "The operator's responsibility" is not a requirement; for sensitive derived data feeding a model, someone will ask where it lives.
12. **Whether the Zeek FoxIO package can emit plain JA4 only** (§6.2, Open Q3). The fallback position depends on this being configurable. If it isn't, "restrict to plain JA4" isn't actually available via that package.
13. **Concurrency mechanism** (Open Q5, §10). Deferred to spec, which is acceptable — but note the device is a global mutex for the whole system, so this interacts with the throughput finding.
14. **Maximum capture size** (Open Q6). Deferred, acceptable for v1, but Zeek memory on a multi-GB capture is a real operational cliff and should get a stated "known-good up to N GB" figure from the spikes.

## Scope larger than it looks

**Name the 60%: §6.4 Tier 1 Detection — PANW VM-Series, together with its enabling infrastructure in §5 "Environment" and §10 "Infrastructure."**

Everything else in this PRD is a Python program orchestrating four well-behaved command-line tools that read files and write files. Ingest, Zeek, Suricata, consolidation, output, provenance, and CLI are perhaps 1,500–2,500 lines with tests, and they are fully testable on a laptop. Tier 1 is a different kind of work entirely: a cloud build, a commercial procurement, a network-topology problem that may be infeasible as designed, a bidirectional-replay problem, a stateful-inspection problem, a fidelity-measurement problem with no published prior art (research C2: "no published measurements of replay-induced missed alerts were found"), an unverified API integration (Open Q7), a clock dependency, and a concurrency constraint. It is also the only part that cannot be tested in CI, the only part with recurring cost, and the only part whose correctness cannot be checked without the lab. It appears in the PRD as five bullet points.

Four other items are bigger than their word count:

- **The admission-filter engine** (§6.3, one bullet). Fetching, parsing rule metadata across ten sources with two different metadata conventions, applying per-source policy, emitting a filtered rule file, hashing it into an addressable snapshot, and reporting per-source admitted counts including a separate JA4 count. This is the component Goal 1 rests on, and it is described as a filter expression.
- **Input normalization** (§6.1, six bullets). Format sniffing, gzip, truncation detection with byte offsets, multi-datalink split, conversion, and provenance recording — with three failure modes that each need defined semantics. Every real-world pcap oddity lands here.
- **The lab build itself** (research brief, "out of scope — deferred, not dropped": "Designing *and building* the lab environment… is a required project deliverable"). This is a project-sized deliverable currently represented in the PRD by one P2 user story (US-12, the diagram).
- **A pipeline-capable CI** (§11's "measured in CI"). Pinned Zeek + Suricata + Wireshark + zkg in a container, plus fixtures that don't contain real traffic. Prerequisite for Goal 2 and for the provenance metric.

## Simpler alternatives worth considering

**1. Ship v1 as Tier 2 only. Make the no-NGFW mode the default, and Tier 1 the v2 milestone.** This is the recommendation. It inverts research decision 8 and relaxes decision 7 (lab as a v1 requirement) — both were made before anyone tested whether the lab is buildable. What you get: a working labelling pipeline for DMEs in weeks instead of after a cloud build and a procurement; a fully deterministic system (all of Goal 2 becomes attainable); everything testable in CI; zero recurring infrastructure cost; and the correlation problem reduced to its tractable half. What you give up: PANW's App-ID-based detections, which research A5 confirms have no free equivalent — a genuine loss, but one that is *additive* later, because §6.6's `sources[]` and tier fields already accommodate a tier arriving afterwards. The architecture the PRD chose (Approach B) makes this a configuration decision, not a rewrite — which is the strongest argument for Approach B and worth cashing in. The honesty machinery already exists: a Tier-2-only run is stamped as lacking Tier 1 coverage, so nobody is misled.

**2. If Tier 1 stays in v1, move the lab off GCP.** A single host with nested virtualisation, Linux bridges, and veth pairs gives you a real Layer 2 segment where `tcpreplay` of original frames actually works, at a fraction of the cost and configuration surface. This may be *the only* configuration in which the vwire design functions at all.

**3. Collapse the lab from three hosts to two.** Suricata reads the file; it has no reason to be a separate machine. This removes a VM, a clock relationship, and a network path.

**4. Drop the millisecond clock requirement** to sub-second with a padded query window, per the Medium finding.

**5. Replace "byte-identical" with "identical after canonicalisation."** Byte-identity across a four-tool chain is a brittle bar that will be quietly abandoned. Canonical-form comparison with explicit determinism controls (fixed Zeek seed, single-threaded Suricata, sorted output, pinned versions) is a bar you can actually hold, and it tests the property you care about.

**6. Add the benign canary instead of reopening corpus validation.** One clean capture, one known-malicious capture, two assertions. It answers the "unfalsifiable" risk at a fraction of the cost of the thing that was declared out of scope.

## What is sound

These are decisions I would not change, and several are better than what I usually see at this stage:

- **Approach B (§10, research C1).** Confining replay to the one component that cannot avoid it is the right call, and it is what makes the "ship Tier 2 first" alternative available at all. The reasoning that `--offline` becomes a consequence of the architecture rather than a bolted-on mode is correct.
- **`unmatched_detections[]` (§6.5).** Emitting a detection you cannot place, with a reason and the raw device fields, rather than dropping it or guessing a flow, is exactly right for training data. So is surfacing the count as a health signal.
- **Refusing to assert benign (§3, §6.6).** Stating "an unlabeled flow is *unlabeled*, not verified benign" **inside the output schema** so the distinction cannot be lost downstream is a genuinely good instinct.
- **Fail-closed on untagged rules (§6.3).** Excluding ET rules with no `confidence` tag is the right default, and filing issue #10 to revisit rather than hand-waving it is the right process.
- **Recognising that ET Open and the IOC feeds are two different classes of source (research A3).** Catching that a single global filter would have silently admitted ET Open alone — and documenting the correction rather than quietly fixing it — is the highest-quality reasoning in the research document.
- **The JA4 capability-versus-content split with an admitted-count canary (§6.3, US-15).** "Because an inactive path is indistinguishable from a broken one, the run records how many JA4 rules were admitted" is the single best sentence in this PRD. It generalises: the same reasoning should be applied to every path that can be empty for legitimate reasons.
- **Sibling run directories, and the explanation of why there is no `latest` symlink (§6.6).** Correct, and the reasoning is recorded so nobody re-adds it.
- **Dropping `--topspeed` (research decision 4) and documenting the tap-vs-vwire trade-off** rather than asserting a winner.
- **Dropping the abandoned abuse.ch JA3 feed (research B1)**, and specifically noticing that the *file* regenerates every five minutes while the *content* is frozen since 2021 — so an mtime freshness check would have reported it healthy. That is real diligence.
- **CLI discipline (§6.7, §8).** stderr for humans, files for machines, never interleaved; distinct exit codes; UTF-8; no colour-only information; "silence is never used to signal a problem."
- **`labels.json` schema version (§6.6, US-13).**
- **The evidence note in §1** disclosing that the problem framing is internally asserted rather than customer-validated. Few PRDs are that honest about their own foundations, and it makes the document easier to trust elsewhere.
- **Secret and capture-data discipline** (`CLAUDE.md`, `.gitignore`, `.env.example`) is real and already in the repo — the only defect is that it also blocks the test fixtures, which is a two-line fix.

## Verification status of the two Critical external claims

Added after the review, by the orchestrating session, before presenting findings. Neither claim was taken at face value.

**Critical 1 (VM-Series vwire in GCP): could not be confirmed or refuted from primary sources.** Palo Alto's "About the VM-Series Firewall" page does not publish a per-platform deployment-mode matrix; the GCP deployment-models URL cited returned 404. The one supporting data point found is Palo Alto's statement that "active/active deployment is supported in virtual wire and Layer 3 deployments on **some private cloud hypervisors**," which associates vwire with private-cloud platforms but does not settle cloud support. **The finding stands regardless of the specific mechanism**, because its core criticism is independently valid: the research's only evidence for vwire was a community post about replaying at a *physical* device, which does not establish behaviour in a cloud VPC. An unverified assumption is recorded in §10 as a settled architecture decision. Spike 1 is the correct resolution either way.

**Critical 2 (Zeek `uid` determinism): partially confirmed, and directionally supported.** Zeek issue #914 confirms Zeek output is non-deterministic across identical pcap runs (analyzer field ordering differs between runs). The `uid`-specific claim was not confirmed from documentation in the time available. Zeek does expose a seed-file mechanism for controlling its RNG. Spike 3 — run Zeek twice over one pcap, diff the `uid`s — settles it definitively in under a day and is the cheapest item on the spike list.
